# 크롤링 파이프라인 아키텍처 (arc42)

- **작성일**: 2026-09-03
- **대상**: 웹 후기 수집 → 정제 → 주차장 연결 → 요약·스코어링에 이르는 파이프라인 전체
- **관련 문서**: [scheduler-pipeline.md](./scheduler-pipeline.md) (기존 운영 문서) · [scoring-recompute.md](./scoring-recompute.md) · [competitors.md](./competitors.md)
- **수치 규약**: 표기 없음 = remote D1 실측(2026-09-03). 근거 없는 것은 **미확인**.

## 1. 서론과 목표

### 1.1 파이프라인이 하는 일

전국 주차장 31,994곳에 대해, 웹에 흩어진 주차 경험을 모아 **"여기 대기 쉬운가"** 를 답할 재료로 바꾼다.

### 1.2 품질 목표 (우선순위 순)

| # | 목표 | 왜 이 순서인가 |
|---|---|---|
| 1 | **정확성** — 틀린 요금·주소·주차장 매칭을 내보내지 않는다 | 사람을 엉뚱한 곳으로 보내거나 돈을 준비 못 하게 만든다. 다른 어떤 이득도 이걸 상쇄하지 못한다 |
| 2 | **고유성** — 남의 글을 그대로 싣지 않는다 | 저작권 문제이자 검색엔진의 저품질 판정 근거다 |
| 3 | **비용** — D1 무료 티어(rows_read 5M/일) 안에서 돈다 | 무료 전환이 진행 중이다 |
| 4 | **신선도** — 새 글이 며칠 안에 반영된다 | 위 셋보다 뒤다. 늦게 맞는 게 빨리 틀리는 것보다 낫다 |

### 1.3 이해관계자

| 역할 | 관심사 |
|---|---|
| 사이트 이용자 | 이 주차장 대기 쉬운가 · 얼마인가 · 만차면 어디로 가나 |
| 운영자(1인) | 손이 덜 가는가 · 비용이 예측되는가 · 틀린 데이터가 안 나가는가 |
| 검색엔진 | 이 페이지에 고유한 가치가 있는가 |

## 2. 아키텍처 제약

| 제약 | 내용 | 파이프라인에 미치는 영향 |
|---|---|---|
| Cloudflare Workers | 호출당 **subrequest 1,000**, CPU 30초 | 한 크론 사이클의 배치 크기가 여기서 결정된다. naver 50 lot·ddg 50 lot 이 상한 |
| D1 (SQLite) | 무료 **5M rows_read/일**, 100k rows_written/일, 500MB/DB | 전수 스캔 금지. 2026-08 에 `crawl_queue`(인덱스 조회)로 바꿔 12배 절감 |

| crawl4ai 온프레미스 | 본문 수집을 여기에 의존 | 이 서버가 죽으면 파이프라인이 **조용히 0건**이 된다 (2026-07-10 사고) |
| AI 모델 | 셀프호스팅 Unsloth(OpenAI 호환). `ANTHROPIC_API_KEY` 는 만료 | 옛 Anthropic 경로 코드는 실행 불가 상태 |
| 운영 인력 | 1인 | 수동 단계가 남으면 **안 돌아간다.** §11 의 최대 부채가 이것이다 |

### 3.1 비즈니스 컨텍스트

```
        ┌──────────────┐
        │ 네이버 검색   │──┐
        │ DuckDuckGo   │  │
        │ Brave        │  ├─► [파이프라인] ─► 주차장 상세페이지 ─► 이용자
        │ YouTube      │──┘         │
        └──────────────┘            │
        ┌──────────────┐            ▼
        │ 공공데이터    │──────► parking_lots (정본)
        │ 카카오/네이버 │
        └──────────────┘
        ┌──────────────┐
        │ 이용자 리뷰   │──────► user_reviews ──► 요약 근거 [1순위]
        └──────────────┘
```

### 3.2 기술 인터페이스

| 상대 | 방향 | 용도 |
|---|---|---|
| 네이버 검색 API | out | 블로그·카페 검색 |
| DuckDuckGo (crawl4ai 경유) | out | 웹 검색 |
| Brave Search API | out | 웹 검색 |
| YouTube Data API | out | 영상 검색 (10,000 units/일) |

## 4. 솔루션 전략

| 결정 | 이유 |
|---|---|
| **raw → 정제 2단 테이블** (`web_sources_raw` → `web_sources`) | 원문은 임시, 정제 결과만 영구. purge 로 용량을 회수한다 |
| **본문을 별도 테이블로 분리** (`web_sources_raw_body`) | purge 가 UPDATE 가 아니라 DELETE 가 되어 페이지가 실제로 회수된다 (0048) |
| **중복 판정을 raw 와 분리** (`seen_sources`) | raw 를 지워도 재크롤하지 않는다 (0050) |
| **대상 선정을 인덱스 조회로** (`crawl_queue`) | 31,994행 스캔 → 인덱스 조회. rows_read 12배 절감 (0052) |
| **rule 필터 우선, AI 는 최소** | AI 호출이 가장 비싸다. 명백한 것은 규칙으로 거른다 |
| **정보 모음 사이트 차단** | 경쟁사가 재배포한 공공데이터를 후기로 세면 요약·평점·색인이 모두 오염된다 |
| **없는 값은 만들지 않는다** | 계산 불가는 0 이 아니라 "모름". 목표 1(정확성)의 구체화다 |

## 6. 런타임 뷰

### 6.1 크론 A — 메인 (`0 */2 * * *`, 하루 12회)

```
1. 수집    naver(50 lot) → youtube(4 lot) → brave(1일 1회)
2. 본문    raw-fulltext-batch
3. 필터    대상 id 선정 → source-filter-queue (회당 1,000건까지)
4. 매칭    match-to-lots (50건) — AI 호출 2종(매칭 검증 · 글 요약)
5. 스코어링 큐가 없을 때만 (폴백)
5.5 큐 동기화 (하루 1회 게이트)
6. purge   terminal 행 본문 삭제
```

**여섯 단계가 한 번의 invocation 안에서 순차로 돈다.** 그래서 한도가 합계에 걸린다.

| 한도 | 값 | 여유 |
|---|---|---|
| wall time | 15분 | 4단계 최악 100분 (50건 × 120초) — **넘는다** |
| CPU time | 30초 | 대부분 I/O 대기라 여유 |
| subrequest | 1,000회 | naver ~500 + crawl4ai 100 + AI — 빠듯 |

2026-09-03 실측으로는 안 터진다. 4단계가 **굶고 있어서**다 — 3단계가 회당 100건인데
유입이 하루 1,877건이라 밀린 것이 **753건**이었고, 4단계에 도달하는 양은 회당 3~4건이었다.
3단계 상한을 올리거나 백로그가 풀리는 순간 이 여유는 사라진다.

> 미필터 행을 그냥 세면 2,187건이 나오는데 그 중 1,469건이 `youtube_video` 다.
> 이 단계는 영상을 건드리지 않는다 (본문 길이가 rule-filter 임계에 못 미쳐
> `scripts/verify-youtube-raw.ts` 가 따로 맡는다). **실제 밀린 양은 753건**이다.
> 백로그를 셀 때 `AND source != 'youtube_video'` 를 빼먹으면 3배로 부풀어 보인다.

방어 장치 두 가지를 4단계에 넣었다.

- **시간 예산** — 6분을 넘기면 남은 raw 를 건드리지 않고 나온다. `matched_at` 을 찍지
  않았으므로 다음 회차가 그대로 이어받는다.
- **증분 flush** — 10건마다 쓴다. 예전에는 50건을 다 돌고 마지막에 한 번 썼기 때문에
  루프 도중에 잘리면 그 회차의 AI 호출이 통째로 버려졌다.

### 6.2 크론 B — DDG 전용 (`30 */2 * * *`, 하루 12회)

subrequest 한도를 메인과 분리하려고 뗐다. `ddg(50 lot)` + `raw-fulltext-batch`.

> **2026-09-03 수정**: 이 크론은 **한 번도 돌지 않고 있었다.** `worker-entry.ts` 가
> `controller.cron === '30 */1 * * *'` 로 문자열 전체를 비교하는데, 2026-08-19 에 주기를
> 매시→2시간(`30 */2 * * *`)으로 바꾸면서 이 줄을 놓쳤다. 조건이 영원히 거짓이라 :30
> 트리거가 else 로 떨어져 **메인 파이프라인이 두 번 돌았다**. 실측: 7일간 ddg 유입 0건,
> 마지막 크롤 시각 `00:31` 이 naver·youtube. 지금은 **분(minute) 필드만** 보고 라우팅한다.

### 6.3 크론 C — 종합 요약 (`45 * * * *`, 하루 24회)

`ai_summary_stale = 1` 인 주차장을 **회당 6곳** 만든다. 메인에 붙이지 않은 이유는 wall
time 이다 — 메인은 이미 AI 호출을 수십 건 담고 있고, 요약은 실측 건당 17~20초다.

대상 선정은 이용자 리뷰가 있는 곳 우선, 그다음 근거가 많은 순이다. 리뷰 보유 lot 이
87곳뿐이라 뒤로 밀리면 순서가 영영 오지 않는다.

**표시(stale)는 한 번 뽑히면 반드시 풀린다.** 안 그러면 한 곳이 매 회차 상한을 먹는다.

| 결과 | stale | 이유 |
|---|---|---|
| 생성 성공 | 0 | |
| 근거 0건 | 0 | 다시 골라도 같다 |
| 품질 가드 거부 | 0 | 같은 입력이면 같은 출력이다 |
| 네트워크·타임아웃 | **1 유지** | 일시적이다. 다음 회차가 다시 시도한다 |

### 6.4 큐 — source-filter-queue

크론 A 3단계가 **id 만 골라 넘기고**, 판정은 소비자가 배치 100으로 한다.
AI 를 쓰지 않아 건당 10ms 미만인데 크론에 묶여 회당 100건이던 것이 백로그의 원인이었다.

| 설정 | 값 | 근거 |
|---|---|---|
| `max_batch_size` | 100 (최대) | AI 없음. 배치가 작으면 D1 왕복만 늘어난다 |
| `max_batch_timeout` | 5초 | |
| `max_retries` | 3 | |
| `dead_letter_queue` | `source-filter-dlq` | 최종 실패를 조회 가능한 형태로 남긴다 |

멱등성은 `ai_filtered_at IS NULL` 을 **SELECT 조건**에 둬서 얻는다. 중복 배달된 메시지는
조회 단계에서 사라지므로 두 번 쓰지 않는다.

> **`max_retries` 는 재생산을 막지 못한다.** 생산자 조회 조건이 같은 `ai_filtered_at IS NULL`
> 이라, 계속 실패해 DLQ 로 간 행도 두 시간 뒤 다시 큐에 들어온다. 그래서 마지막 배달
> (`attempts >= 3`)까지 실패한 행은 `filter_removed_by = 'consumer_error'` 로 종결 표시해
> 생산자 대상에서 빼낸다. 값은 지우지 않는다 — 왜 빠졌는지는 남는다.

DLQ 는 **읽는 사람이 없으면 목록일 뿐이다.** 4일 뒤 만료되고 알림도 없다.
확인은 대시보드나 `wrangler queues consumer` 로 한다.

> ⚠️ **D1 은 쿼리당 바인딩 파라미터를 100개까지만 받는다.** `IN (...)` 에 배치 100을
> 그대로 넣으면 한계에 걸터앉는다. 소비자는 90건씩 잘라 조회한다.
> `score-recompute-queue` 의 배치 25도 같은 이유로 올리면 안 된다 —
> `scoring-engine` 이 lot id 를 두 번 바인딩해서 25가 곧 50이다.

### 6.5 큐 — score-recompute-queue

생산자는 두 곳이다. 이용자 리뷰(`reviews.ts`)와 매칭(`match-to-lots.ts`).
소비자는 평점을 다시 계산하고, **종합 요약을 다시 만들 만한 변화인지 판정해 표시만** 한다.
AI 호출은 하지 않는다 — 큐 배치는 빨라야 한다.

| 변화 | 표시 조건 |
|---|---|
| 이용자 리뷰 등록·삭제 | **조건 없이** (1순위 근거이고, 대상이 87곳뿐이라 비용이 미미하다) |
| 웹 근거 매칭 | 요약이 없거나 · 새 근거 3건 이상 · 마지막 요약 90일 경과 |

큐에 안 들어가는 경로가 둘 있어서(매칭 루프가 예산에 걸려 끊김 / `sendBatch` 실패)
크론 A 5단계가 **재투입 보정**을 한다. `matched_at > computed_at` 인 lot 만 다시 큐에
넣으므로, 정상 경로에서는 0건이고 빠진 것만 잡힌다. 재계산을 직접 하지는 않는다.

## 8. 횡단 개념

### 8.1 데이터 신뢰 등급

파이프라인 전체가 이 등급을 따른다.

| 등급 | 무엇 | 취급 |
|---|---|---|
| **정본** | 공공데이터 주차장 정보 | 덮어쓰기 기준 |
| **1순위 근거** | 이용자 리뷰 (`is_seed=0`) | 요약에서 웹보다 앞선다. 별점 마크업은 이것만 |
| **2순위 근거** | 블로그·커뮤니티 (정보 모음 사이트 제외) | 요약 재료. **원문은 화면에 싣지 않는다** |
| **참고** | 시드 리뷰 (`is_seed=1`) | 단독 근거로 쓰지 않는다 |
| **배제** | 정보 모음 사이트 · 우리 사이트 | 수집·집계·색인 신호 전부에서 제외 |

### 8.2 근거 배분 기준

우선순위를 프롬프트 문장으로 두면 지켜지지 않는다. **입력 개수로 강제한다.**

```
리뷰 없음  → 웹 요약 30건
리뷰 있음  → 웹 요약 min(30, max(4, 리뷰수 × 4))건
```

실측에서 최악이 리뷰 1건 : 웹 21건이었다. 이 기준으로 4:1 이 된다.
구현·테스트: `lib/lot-summary-input.ts`

### 8.3 "없는 값은 만들지 않는다"

| 상황 | 하는 일 |
|---|---|
| 추가 요금 정보 없음 | 계산기를 숨긴다 (0원이라 하지 않는다) |
| 무료 플래그 + 요금표 동시 | 계산기를 숨긴다 (어느 쪽이 맞는지 모른다) |
| 유효 후기 3건 미만 | 분위기 막대를 그리지 않는다 |
| 대안 주차장 이름이 DB 와 안 맞음 | 저장하지 않는다 |
| 실사용자 리뷰 0건 | `AggregateRating` 을 내보내지 않는다 |

### 8.4 오류 처리

각 단계가 `try/catch` 로 감싸여 실패해도 다음 단계가 돈다. 로그는 `console.log` 한 줄.
**약점**: 조용한 실패를 알아채는 장치가 없다 (§11).

## 12. 업데이트 계획

### 1단계 — 걷어내기 ✅ 완료 (2026-09-03)

- `ai-filter.ts` 에 "크론 미사용 + 만료 키" 상태를 파일 머리에 명시
- `raw-fulltext-batch.ts` 의 죽은 파일 참조 주석 정리

### 2단계 — ② 요약을 파이프라인에 넣기 (R1)

**먼저 대량 생성**, 그다음 자동화. 순서가 반대면 크론이 5,882곳을 한꺼번에 처리하려 든다.

| 순서 | 내용 | 게이트 |
|---|---|---|
| 2-a | 파일럿 50곳 | `ai-content-qa-standard.md` 의 PASS+FIX 80%↑ / DROP 20%↓ |
| 2-b | 1차 500곳 | 비용·시간 실측, 실패율 |
| 2-c | 나머지 라운드 반복 | |
| ~~2-d~~ | ~~`scheduled.ts` 에 5.6 lot 요약 추가~~ ✅ 2026-09-03 — 5.6 이 아니라 **별도 크론 C** 로 뗐다 (wall time 분리). 상한은 20 이 아니라 **6** — 실측 건당 17~20초 |

### 3단계 — 크론을 큐로 쪼개기 (R9, R8) — 진행 중

**✅ `source-filter-queue` 완료 (2026-09-03).** AI 가 없어 위험이 가장 낮은 단계를 먼저 옮겼다.
크론 3단계는 이제 생산자일 뿐이고, 판정·재시도·DLQ 는 큐가 맡는다.

배포 직후 수동 실행 실측:

```
filter-enqueue: 753 raws → queue          생산자 (인덱스 조회 1회 + sendBatch 8회)
02:42 100건 / 02:43 653건                 소비자가 약 1분에 소진
match: 1 sources → 2 lot links (2 AI verified, 1 summarized)
match: AI budget exceeded                 6분 예산 소진, raw 39건 처리
lot-summary: 2/2 generated                크론 C
```

`web_sources` 2행이 **ai_summary 와 filter_passed_v2 를 갖고** 들어왔다 —
둘 다 그동안 크론 경로에서는 항상 NULL 이던 값이다.

**매칭 처리량 예상은 틀렸다.** 회당 10~15건으로 봤는데 실측은 **6분에 39건**이다
(회당 468건/일 capacity vs 통과 유입 약 198건/일). 즉 매칭은 정상 상태에서 유입을
따라잡는다. `AI budget exceeded` 는 일회성 백로그가 빠질 때까지만 찍힌다.
`source-match-queue` 는 처리량이 아니라 **실패 격리·DLQ** 를 위해 필요한 것이다.

남은 것은 `crawl-fulltext` · `source-match` · `lot-summary` 다.

지금은 "6단계를 완주하거나, 어디선가 잘리거나" 둘뿐이고 **잘린 지점이 남지 않는다.**
작업 단위를 메시지로 바꾸면 실패가 건 단위로 격리되고, DLQ 가 곧 실패 목록이 된다.

| | 지금 | 큐 |
|---|---|---|
| 작업 단위 | 회차 전체 | raw 1건 / lot 1곳 |
| 실패 격리 | 회차 통째 재시도 | 그 메시지만 `retry()` |
| 실패 가시성 | 로그 문자열 | DLQ 조회 |
| wall 15분 | 6단계 합계 | 배치 하나 |
| subrequest 1,000 | 6단계가 나눠 씀 | 소비자마다 별도 |

```
크론 A (2시간)   수집 → raw 적재 + 큐에 넣기          ← 생산자만
크론 B (2시간)   DDG
크론 C (매시)    종합 요약 (또는 lot-summary-queue 로 이관)

crawl-fulltext-queue   raw_id → 본문        (batch 10)
source-filter-queue    raw_id → rule 필터   (batch 25, AI 없음)
source-match-queue     raw_id → 매칭 + 글 요약 (batch 3, AI 있음)
score-recompute-queue  lot_id → 평점 + stale 표시   ← 이미 있음
lot-summary-queue      lot_id → 종합 요약   (batch 3, AI 있음)
```

**1·2단계(수집·본문)는 큐로 옮기지 않는다.** 외부 API 쿼터가 진짜 병목이라
(YouTube 1만 unit/일, Brave 1일 1회, naver 우선순위 50곳) 빠르게 소비하면 하루치를
한 번에 태운다. 여기는 "얼마나 자주 도느냐"로 제어하는 게 맞다.

**비용**: 100만 작업당 $0.40, 쓰기·읽기·삭제가 각각 1작업. 하루 1,877건 × 3단계 × 3작업
≈ 월 50만 작업 = **월 $0.2**.

**큐가 공짜로 주지 않는 것**: at-least-once 라 같은 메시지가 두 번 온다. AI 단계에서는
그게 그대로 비용이다. 소비자는 반드시 DB 상태(`ai_filtered_at` / `matched_at` /
`ai_summary IS NOT NULL`)로 먼저 걸러야 한다. 큐는 그 컬럼을 대체하는 게 아니라
**그 컬럼을 폴링하던 것**을 대체한다.

### 4단계 — 한 벌로 합치기 (R2)

각 단계 로직을 `lib/stages/` 순수 함수로 뽑고, 크론과 스크립트는 **껍데기만** 갖는다.

```
lib/stages/collect-naver.ts   ← 쿼리 생성·파싱·중복 판정
lib/stages/filter.ts          ← rule + 차단
lib/stages/match.ts
lib/stages/summarize-lot.ts

crawlers/*.ts   → D1 바인딩 + 배치 크기
scripts/*.ts    → local/remote 스위치 + 로그
```

`lib/lot-summary-input.ts`(2026-09-03)가 이 방식의 첫 조각이다. 스크립트가 그 함수를 import 하고, 기준은 `src/` 안에서 테스트된다.

**위험**: 파이프라인 전체를 건드린다. 되돌리기 어렵고 스테이징이 없다(R7). 단계별로 나눠, 한 번에 한 스테이지씩 옮기고 배포한다.

### 5단계 — 감시 (R3, R5)

- crawl4ai 응답 실패율이 임계를 넘으면 크론 로그에 경고 (지금은 pending 0 이 정상인지 장애인지 구분되지 않는다)
- `raw-fulltext-batch` 중복 호출 정리

### 하지 않을 것

- 경쟁사 크롤 — 같은 공공데이터의 사본이다 ([competitors.md](./competitors.md))
- 목적지(POI) 페이지 양산 — 좌표 데이터가 없다
