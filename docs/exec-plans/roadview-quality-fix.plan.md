# 구현 계획: 로드뷰 품질 개선 (엉뚱한 로드뷰 교정)

> 이 문서는 [로드뷰 panoId 전수 수집](./roadview-panoid-full-backfill.plan.md)을 대체한다.
> 기존 계획은 "좌표 자동 탐색 결과를 그대로 저장"하는 것이 목표였는데,
> 그렇게 저장하면 **지금 화면에 나오는 잘못된 로드뷰가 그대로 고정될 뿐**이라는 것이
> Phase B spike에서 확인되었다. 목표를 "올바른 로드뷰를 고르는 것"으로 재정의한다.
>
> **2026-08-06 개정**: 네이버 클라우드 공식 답변으로 **파노라마 결과의 DB 저장이 불가**함이
> 확정됐다. 동시에 **`setPosition()` 반복은 과금되지 않는다**는 답변을 받아, 수집 방식을
> "서버 배치로 미리 모아 저장"에서 **"상세 페이지에서 그때그때 찾기"**로 전환한다.
> 원인·선택 규칙·검증 결과(Phase 2·2b)는 그대로 유효하며, 실행 수단만 바뀐다.

## 문제 정의

주차장 상세 페이지의 로드뷰가 주차장·출입구와 무관한 곳을 비춘다.

대표 사례: **이마트타운 월계점 주차장(`KA-20562951`)** — 트레이더스 월계점이 입점한 건물.
현재 화면에는 건물 뒤편 이면도로의 **빈 외벽**만 나온다.

## 원인 (2026-08-03 실측)

세 가지 원인이 겹쳐 있고, **하나만 고쳐서는 해결되지 않는다.**

### 1. 주차장 좌표가 부지 중심점이다

`KA-20562951`의 등록 좌표 `37.6265483, 127.0618877`은 출입구가 아니라 건물/부지 중심에 가깝다.
카카오 POI 기반 좌표의 일반적 특성이다.

### 2. `Panorama`가 "가장 가까운" 파노라마를 고른다

부지 중심에서 가장 가까운 파노라마는 **건물 뒤 이면도로**(57.9m)다.
주변 파노라마 33개를 반경 0~150m로 프로브한 결과, 실제 정문을 비추는 파노라마는
**84.5m 지점**에 있었다. 즉 **거리와 품질이 역상관**이다.

| 후보 | 거리 | 촬영일 | 화면 내용 |
|---|---|---|---|
| 현재 자동 선택 | 57.9m | 2025-01-22 | 건물 뒤편 빈 외벽 (❌) |
| **#16** | **84.5m** | **2026-02-23** | **이마트타운 정문 출입구·하차장 (✅)** |
| #18 | 86m | 2026-02-23 | 건물 정면, 버스에 가림 (△) |
| #28 | 156m | 2026-02-23 | 전혀 다른 건물의 하역장 (❌) |

### 3. POV가 정북으로 고정되어 있다

`src/components/WikiMiniMap.tsx`가 `pov: { pan: 0, tilt: 0, fov: 100 }`로 파노라마를 띄운다.
`pan: 0`은 **정북**이므로, 주차장이 파노라마 지점의 남쪽에 있으면 반대편을 보게 된다.
월계점은 주차장 방위가 36.6°라 약 37° 어긋난다.

단, **POV만 보정하면 오히려 나빠진다** — 잘못된 파노라마에서 벽을 더 정면으로 볼 뿐이다.
파노라마 선택과 POV는 **함께** 고쳐야 한다.

## 핵심 결정

### 1. "가장 가까운 파노라마" 대신 후보 탐색 + 선택 규칙

주차장 좌표 하나로 조회하지 않고, 주변을 프로브해 후보 파노라마 집합을 만든 뒤 고른다.

프로브: 반경 `0/25/50/75/100/150m` × 8방위 = 41개 좌표 → 유니크 panoId 수집
(월계점 기준 33개, 약 60초 소요)

### 2. 선택 규칙: 근거리 우선 → 아니면 촬영일 최신 그룹 → 최근접

```
if (최근접 거리 <= NEAR_ENOUGH_M)                → 최근접 후보
else if (선택 거리 - 최근접 거리 <= MAX_JUMP_M)   → 촬영 날짜 최신 그룹 → 그중 최근접
else                                              → 최근접 후보
```

`NEAR_ENOUGH_M = 50`, `MAX_JUMP_M = 60`

> `NEAR_ENOUGH_M`은 Phase 2에서 30으로 정했다가 **2026-08-06 라이브 검증에서 50으로 올렸다.**
> 근거는 아래 [가드 상향](#가드-상향-30--50m-2026-08-06)에 있다.

**날짜 그룹핑 근거**: 네이버는 간선도로·건물 정면을 자주 재촬영하고, 이면도로·서비스도로는
오래된 촬영본이 남는다. 월계점의 뒷골목은 2025-01, 정면 도로는 2026-02 촬영이었다.

**근거리 가드 근거**: Phase 2 검증에서 날짜 규칙 단독은 **역효과를 냈다**.
최근접 후보가 이미 2.4m인 노상주차장에서 5일 더 최신이라는 이유로 109m 떨어진
전혀 다른 건물 앞 버스정류장을 골랐다. 최근접이 이미 주차장 바로 앞이면 그대로 쓴다.

**주의**: 날짜가 아니라 시각(datetime)까지 최신으로 정렬하면 같은 날 더 늦게 촬영된
광운로(14:15)가 뽑혀 **전혀 다른 건물**이 나온다. 반드시 **날짜 단위로 그룹핑**한다.

#### Phase 2 검증 결과 (2026-08-05, 15곳)

대형시설(백화점·마트·터미널·공원) + 서울 노상 혼합 샘플. 프로브 격자는 축소본
(반경 0/30/60/100m × 6방위 = **19회**)을 사용했고 lot당 평균 **1.6초**였다.

날짜 규칙만 적용했을 때 최근접과 다른 선택을 한 6곳의 육안 검수 결과:

| 주차장 | 최근접 → 규칙 선택 | 판정 |
|---|---|---|
| 이마트 월계점 | 56.2m(2025-01) → 86m(2026-02) | ✅ 뒷골목 벽 → 정문 |
| 홈플러스 영등포점 | 67.8m(2026-02) → 84.2m(2026-03) | ✅ 길 건너 타 건물 → 홈플러스 본관 |
| 현대백화점 대구점 | 61.4m(2026-03-24) → 62.2m(2026-03-25) | ➖ 차이 미미 |
| 성산포항여객선터미널 | 8.6m(2019) → 25.1m(2025) | ➖ 둘 다 주차장 내부 |
| 아이파킹 이마트 양재점 | 1.9m(2026-01) → 29.1m(2026-04) | ❌ 주차 진입부 → 교차로 |
| 도산대로45길(노상) | 2.4m(2026-01-16) → 109m(2026-01-21) | ❌ 실제 골목 → 타 건물 버스정류장 |

**개선 3 / 무해 2 / 개악 2**. 개악 2건은 모두 최근접이 3m 미만이었고, 개선 케이스는
모두 최근접이 56m 이상이었다. 30m 임계값이 두 군을 깨끗하게 가른다.

#### Phase 2b — 표본 확대 재검증 (2026-08-05, 60곳 추가 / 누적 73곳)

15곳 표본이 대형시설에 치우쳐 있어, 일반 주차장(노외 35·노상 15·부설 10) 60곳을 추가했다.
**결론이 달라졌다.**

**(1) 규칙이 필요한 lot이 생각보다 적다**

최근접 거리 분포: p25 8.8m · p50 15.9m · p75 28.2m.
**최근접이 30m를 넘는 lot은 73곳 중 16곳(22%)뿐**이다.
나머지 78%는 이미 주차장 바로 앞 파노라마가 잡히므로 규칙이 개입할 이유가 없다.
월계점처럼 "최근접이 엉뚱한 뒷골목"인 상황은 실재하지만 흔하지 않다.

**(2) 30m 가드만으로는 부족하다 — 점프 상한이 필요하다**

30m를 넘겨 규칙이 적용된 케이스 중에도 개악이 나왔다.

| 주차장 | 최근접 → 선택 | 판정 |
|---|---|---|
| 롯데백화점일원 | 35.4m → 101.5m | ❌ 백화점 정문 → 고가도로 밑 |
| 꿈빛도서관 옆 | 34.7m → 108.1m | ❌ (동일 패턴) |

둘 다 **+66m 이상 멀어지는 점프**였다. 반면 정상 개선 케이스는 점프가 +0.8~+43m에 그친다.
그래서 `MAX_JUMP_M = 60`을 추가했다.

**(3) 최종 규칙의 실제 영향 범위**

누적 73곳에 최종 규칙(30m 가드 + 60m 점프상한)을 적용하면 **6곳(8%)만 바뀐다.**

| 주차장 | 최근접 → 선택 | 육안 검수 |
|---|---|---|
| 이마트 월계점 | 56.2m → 86m | ✅ 확인 |
| 홈플러스 영등포점 | 67.8m → 84.2m | ✅ 확인 |
| 현대백화점 대구점 | 61.4m → 62.2m | ➖ 차이 미미 |
| 노비아갈라웨딩 | 34.1m → 49m | 미검수 |
| 복사골문화센터 | 47.1m → 90.4m | 미검수 |
| 수주도서관 | 76.9m → 112.3m | 미검수 |

개악 2건은 점프 상한이 차단한다.

**판단 재료**: 전수 적용 비용은 약 5.3시간(동시성 3) + 네이버 호출 61만 회인데,
**실제로 화면이 개선되는 것은 8% 수준**이다. Phase 3 착수 여부를 이 비율로 다시 판단할 필요가 있다.
대안으로 "최근접 30m 초과 lot(22%)만 프로브" 하면 비용이 1/5로 줄고 효과는 동일하다.

(이 비용 계산은 전수 배치를 전제한 것이라 런타임 전환 이후 무의미해졌다. 아래 [적용 범위](#적용-범위) 참고)

#### 가드 상향: 30 → 50m (2026-08-06)

Phase 3 구현 직후 라이브 페이지에서 두 곳을 열어봤는데, 두 번째 주차장에서 **개악이 나왔다.**

| 주차장 | 최근접 → 규칙 선택 | 판정 |
|---|---|---|
| 미사경정공원 P1 | 43.6m(2024) → 73.8m(2025-09-04) | ❌ **주차 구획·횡단보도 → 공원 외곽 도로 가드레일** |

점프가 +30m라 `MAX_JUMP_M`에 걸리지 않고, 최근접이 43.6m라 30m 가드도 통과한다.
**두 가드 사이의 사각지대**다.

이 관점으로 Phase 2·2b 표를 다시 보면 패턴이 분명하다.

- 육안으로 **개선이 확인된 사례는 최근접 56.2m·67.8m** 둘뿐이다
- **30~50m 구간에는 확인된 개선이 하나도 없다** — 개악 35.4m·34.7m(점프 상한이 차단)·43.6m(차단 실패),
  미검수 34.1m·47.1m

즉 30이라는 값은 "개악을 막는 하한"으로 잡혔을 뿐, 그 위 구간에 개선이 있다는 근거는 없었다.
50으로 올리면 확인된 개선 2건은 그대로 살아남고 근거 없는 개입 구간만 사라진다.

**측정 방법 메모**: "최근접이 어떻게 보이는지"는 구현된 *사용자 조작 시 교체 취소* 가드를 이용해
확인했다. 파노라마가 뜬 직후 컨테이너에 `pointerdown`을 넣으면 교체가 취소되어 최근접 파노라마가
그대로 남는다. 단, 리스너는 SDK 로드 완료 후에 붙으므로 **그 전에 이벤트를 쏘면 무시된다**
(첫 시도가 이것 때문에 무효였다).

### 3. `title`(도로명)은 선택 신호로 쓰지 않는다

정문을 비추는 #16의 `title`은 빈 문자열이고, 엉뚱한 #28은 `광운로`였다.
도로명 유무는 품질과 무관하다. 리포트 표시용으로만 쓴다.

### 4. POV는 파노라마 → 주차장 방위각으로 계산한다

```
pan = 정방위각(파노라마 좌표 → 주차장 좌표)
```

항상 런타임 계산이다. 저장할 수 없기도 하고, 파노라마가 바뀌면 방위각도 같이 바뀌어야 하므로
저장할 이유도 없다. (Phase 1에서 `aimAtLot()`으로 구현 완료)

### 5. 자동 선택은 "개선"이지 "정답"이 아니다 — 검수 경로를 함께 만든다

자동 규칙으로 대부분을 개선하되, 남는 곳은 사람이 검수해 **출입구 좌표**를 지정한다(Phase 4).
panoId를 수동으로 덮어쓰는 방식은 저장 금지에 걸리므로 쓰지 않는다.

## 데이터 모델 — 없음 (저장 금지)

**네이버 공식 답변으로 파노라마 결과의 DB 저장이 불가해졌다**(아래 [약관 확인 결과](#약관과금-확인-결과-2026-08-06--네이버-클라우드-공식-답변)).
따라서 `roadview_pano_id`·`roadview_lat/lng`·`roadview_photodate` 등을 `parking_lots`에
적재하려던 초안 스키마는 **폐기한다. 마이그레이션 없음.**

후보 탐색과 선택은 **상세 페이지가 열릴 때 브라우저에서 수행하고, 결과는 그 페이지 수명 동안만
메모리에 둔다.** 서버·D1·로컬스토리지 어디에도 남기지 않는다.

저장이 허용되는 것은 **네이버 호출에서 유래하지 않은 우리 데이터**뿐이다. 원인 #1(주차장 좌표가
부지 중심)에 대한 근본 해법인 **사람이 지도를 보고 지정한 출입구 좌표**가 여기 해당하며,
이는 Phase 4에서 다룬다.

### Phase 3 — 런타임 선택 (배치 수집기를 대체)

저장이 막히고 `setPosition()` 반복이 무과금으로 확인되면서, 같은 규칙을 **상세 페이지가 열릴 때
브라우저에서** 돌린다. 서버 배치·스키마·재개 로직이 통째로 사라진다.

```
1. lot 좌표로 Panorama 생성 → pano_status=OK → getLocation()   (Phase 1에서 이미 구현됨)
2. 거리 ≤ NEAR_ENOUGH_M(50m)  → 그대로 두고 POV만 보정            ← 대다수
3. 거리 > NEAR_ENOUGH_M       → 화면 밖 두 번째 인스턴스로 프로브
                                → 선택 규칙 → 표시 인스턴스에 반영
```

- [x] `src/lib/roadview-select.ts` — 프로브 격자 + 선택 규칙을 순수 함수로 분리 (단위 테스트 대상)
- [x] `WikiMiniMap.tsx` — 가드 초과일 때만 프로브 후 교체
- [x] Phase B spike 제약 반영: 인스턴스 재사용 시 실패하면 직전 panoId가 남으므로

- [x] 프로브는 화면에 이미 로드뷰가 뜬 뒤 백그라운드로 진행 (첫 표시를 지연시키지 않는다)
- [x] 사용자가 로드뷰를 조작한 뒤에는 교체하지 않는다 (시야를 빼앗지 않는다)
- [x] 라이브 검증 — 월계점에서 후보 16개 수집, 56.2m → 86.0m 교체, 정문 표시 확인

### Phase 4 — 출입구 좌표 (근본 해법, 우리 데이터)

원인 #1은 파노라마 선택이 아니라 **주차장 좌표가 부지 중심**이라는 것이다. 사람이 지도를 보고
지정한 출입구 좌표는 네이버 결과 데이터가 아니므로 저장할 수 있고, 로드뷰뿐 아니라 지도 마커·
길안내에도 함께 쓰인다.

- [ ] `parking_lots.entrance_lat` / `entrance_lng` (사람이 입력한 값만 채운다)
- [ ] 로드뷰·마커가 출입구 좌표가 있으면 우선 사용
- [ ] 입력 경로 (관리자 화면 또는 스크립트)

우선순위는 Phase 3보다 낮다. Phase 3이 자동으로 개선하지 못하는 잔여 케이스를 받는 자리다.

## 적용 범위

전수 배치라는 개념이 사라졌다. 프로브는 **로드뷰 탭을 실제로 연 사용자의 브라우저에서, 최근접이
가드(50m)를 넘는 주차장에 대해서만** 발생한다. 3.2만 곳을 미리 훑을 이유가 없다.

비율은 실측 분포(p25 8.8m · p50 15.9m · p75 28.2m)상 30m 초과가 22%였으니 50m 초과는 그보다
작은 부분집합이다. 정확한 값은 재측정하지 않았다.

lot당 18회 프로브는 헤드리스 기준 약 1.5초였고, 실사용 네트워크에서는 3~5초로 본다. 첫 로드뷰가
이미 표시된 뒤 백그라운드로 진행되므로 체감 지연이 아니라 **뒤늦은 개선**으로 나타난다.

## 약관·과금 확인 결과 (2026-08-06) — 네이버 클라우드 공식 답변

2026-08-05 조사에서 미확인으로 남겨둔 4개 항목에 대해 네이버 클라우드에서 답변을 받았다.
아래가 확정 사실이며, 이전 조사 메모(2차 출처 기반 추정)는 이 답변으로 대체한다.

| 질문 | 답변 | 결과 |
|---|---|---|
| `getLocation()` 결과(panoId·좌표·촬영일)를 자사 DB에 저장 후 재사용 | **"호출 데이터의 DB 저장은 허용되지 않습니다. 따라서 문의하신 방식으로 이용하는 것은 불가합니다."** | 배치 백필·스키마 폐기 |
| `setPosition()` 반복의 호출 건수 산정 | **"지도 로딩 이후 사용하는 Panorama는 호출 건수에 포함되지 않습니다."** | 프로브 무과금 |
| Panorama 무료 이용량 포함 여부 | **"Panorama는 호출 이후 이루어지는 기능으로, 별도의 이용량 기준이 없습니다."** | 한도 관리 불필요 |
| 헤드리스 브라우저로 3.2만 건 일회성 배치 | **"특별한 제약은 없습니다. 가급적 초당 20회 이내 권장."** | 조사 스크립트 존치 가능 |

**해석**: 저장은 막혔지만 호출은 사실상 무제한·무과금이다. 계획의 방향이 "미리 모아서 저장"에서
"필요할 때 브라우저에서 찾기"로 뒤집혔고, 2번 답변이 없었다면 런타임 프로브는 과금 부담 때문에
성립하지 않았을 것이다. 즉 **폐기된 전제가 곧 대안의 근거**가 됐다.

**남는 경계**: 저장 금지의 대상은 "호출 데이터"다. 사람이 지도를 보고 직접 지정한 출입구 좌표는
여기에 해당하지 않는다고 보고 Phase 4를 진행한다. 반대로 프로브 결과에서 **자동으로 파생시킨 값은
플래그 한 칸이라도 저장하지 않는다** — 회색지대에 들어가지 않는 편이 낫다.
