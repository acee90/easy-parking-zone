## 1. v2가 바꾸는 한 가지

> 크롤링 원문을 **필터링만 해서 그대로 노출**하던 것을,
> 크롤링 원문에서 **뽑아낸 산출물 + 근거 링크**로 대체한다.

원문은 화면에서 사라지고, 출처 목록의 링크로만 남는다.

### 왜

라이브 실측(2026-09-02, Googlebot UA):

| 관측 | 값 |
|---|---|
| 블로그 3건 이상 페이지에서 스크랩:자체 비율 | 8/8 전부 스크랩 우세, 최대 **6.03배** |
| 렌더된 블로그 카드 중 원문 스니펫 그대로 | **60.7%** (rel≥40 행 10,852/17,875) |
| 출처 사이트 크롬 SSR 노출 | 41건 중 4건 (최악 10회) |

> ⚠️ **단정하지 말 것**: 이것이 색인 실패의 원인이라는 증거는 없다. GSC의 「크롤링됨-미색인」 대 「검색됨-미색인」 건수를 먼저 확인해야 한다 (own-content-strategy.md §2-3).
> v2는 색인 대책이 아니라 **콘텐츠 품질 대책**으로 정당화된다.

## 3. 정제 산출물 카탈로그

### 3-1. 지금 데이터로 즉시 가능

| 산출물 | 원천 | 보유 | 비고 |
|---|---|---:|---|
| **웹 후기 분위기** | `web_sources.sentiment_score` | 13,376행 / **7,330 lot** | 아래 §3-2 |
| **후기 신선도** | `web_sources.published_at` | 8,924행 | "2026년 후기 2건" 표기 |
| **소스 분류 / 정보 모음 사이트 제외** | `source_url` 도메인 | 전 행 | 도메인 차단 목록만으로 시작 |
| **주변 비교표 · 도보 N분 · 요금 파생** | `parking_lots` | 좌표 100% / 요금 계산 가능 **5,420** | own-content-strategy §4 B1~B7 |

### 3-2. ⭐ `sentiment_score`는 이미 1–5 스케일이다

```
min 1.0 / max 5.0 / avg 3.527   (filter_passed_v2=1 & sentiment NOT NULL)
```

**별점 데이터를 새로 만들 필요가 없다.** lot 단위로 평균만 내면 된다.

lot당 유효 후기 수 분포:

| 유효 후기 | lot 수 |
|---|---:|
| 1건 이상 | 7,330 |
| **3건 이상** | **1,116** |
| 5건 이상 | 302 |
| 10건 이상 | 78 |

**게이트: 3건 미만이면 렌더하지 않는다.** 1건짜리 평균은 평점이 아니다.

> ⚠️ **위 건수는 정보 모음 사이트 제외 전 값이다.** 0-1(도메인 차단)을 적용하면 실제 lot 수는 이보다 줄어든다.
> 샘플 lot에서도 14건 중 2건이 정보 모음 사이트라 평점이 3.7 → **3.8(12건 기준)** 으로 바뀐다.
> 순위와 우선순위는 바뀌지 않으므로 재측정은 0-1 배포 후 한 번에 한다.

> 🚨 **schema.org `AggregateRating`으로 내보내면 안 된다.** AI 추정값이다.
> 별점 마크업은 실사용자 리뷰 보유 **87개 lot**에만 허용된다.
> (현재 코드는 `parking-jsonld.ts:33-41`에서 난이도 점수 기준으로 ~31,939 페이지에 출력하고, 리뷰 0건이면 `ratingCount: 1`을 지어낸다 — 별도 수정 필요.)

### 3-3. 정규화가 필요한 것

**특징 태그** — `ai_difficulty_keywords`, 3,085 lot 보유. 값이 원형 그대로라 같은 개념이 흩어져 있다.

```
["혼잡"] 938  ["경사"] 302  ["불편"] 275  ["넓"] 220  ["기계식"] 161
["만차"] 158  ["공영"] 157  ["좁"] 141   ["진입"] 103 ["어렵"] 102
["좁다"] 90   ["넓음"] 86   ["기둥"] 70   ["넓다"] 67  ["협소"] 55
```

`좁/좁다/협소` → **협소**, `넓/넓음/넓다` → **넓음**, `혼잡/만차/복잡` → **혼잡** 식의 사전 매핑 1개면 된다. AI 호출 불필요.

### 3-4. 신규 구현 — 경쟁사에 없는 것

**대안 주차장 추출.** 후기 본문에 등장한 주차장 이름을 `parking_lots`와 대조해 연결한다.

샘플 lot에서 실제로 관측된 것:

| 언급된 주차장 | 후기 건수 | 근거 |
|---|---:|---|
| 인천내항 8부두 주차장 (무료) | 5 | "넓고 시간제한이 없다", "도보 약 10분" |
| 송월동 동화마을 공영주차장 | 3 | "주말에 자리가 없어 도보 5분 거리 동화마을에 주차" |
| 한중문화관 공영주차장 | 1 | "공영·민영 요금 총정리"에서 함께 비교 |

**이게 사람들이 그 블로그를 읽는 진짜 이유다.** 지금은 이 정보가 근중복 블로그 덤프 7건 안에 묻혀 있다.
부수 효과로 **내부 링크가 늘어난다** — own-content-strategy가 지적한 RC-4(지역 허브 없는 lot)에도 직접 작용한다.

### 3-5. 보류

| 산출물 | 이유 |
|---|---|
| 실측 요금 vs 공시 요금 대조 | 오탐 시 **잘못된 요금 안내**가 된다. 사용자 피해가 실질적 |
| 혼잡 시간대 신호 | 별도 파이프라인 불필요 — 태그 사전 확장으로 흡수 |

### 3-6. ⑤ 요금 계산 — 공식 정정 (2026-09-02)

`own-content-strategy.md` B3의 근사식 `base_fee*60/base_time`은 **폐기됐다.** 유료 lot의 33%에서 틀린 값을 낸다.

```
이용시간 ≤ base_time              → base_fee
이용시간 > base_time              → base_fee + ceil((이용시간 - base_time) / extra_time) × extra_fee
daily_max 가 있으면               → min(위 결과, daily_max)
extra_time / extra_fee 가 없으면  → 계산하지 않고 "요금 정보 부족"으로 표시
```

| 구분 | 건수 |
|---|---:|
| `base_fee>0 AND base_time>0` | 9,266 |
| └ 근사식이 오답을 내는 lot (`extra_*` ≠ `base_*`) | **3,057 (33.0%)** |
| └ `extra_*` 결손 → 계산 불가, **숫자를 지어내면 안 됨** | **3,846 (41.5%)** |
| **= ⑤ 블록을 켤 수 있는 lot** | **5,420** |

시안의 계산기는 이미 이 공식으로 구현돼 있다 — 문서 쪽이 틀렸던 것이다.

## 4. 화면 구성

시안 참조. **표시 순서**와 조건은 아래와 같다. 번호는 블록 ID이며 논의·문서 참조용으로 고정한다(표시 순서와 일치하지 않는다).

> **순서 원칙 (2026-09-02 재배치)** — 댓글 피드백 반영.
> **사람이 쓴 것 → 기계가 요약한 것 → 돈·대안 → 부가**
>
> 1. **사람** — 평가 지표 ② (이용자 별점 + 웹 후기 분위기) → 이용자 후기 ⑧ → 평가 남기기 ⑦
> 2. **기계** — 후기 종합 ① (자주 나온 말 흡수, ③ 폐지)
> 3. **돈·대안** — 요금 계산 ⑤ → 주변 비교 ⑥ → 함께 언급된 주차장 ④
> 4. **부가** — FAQ ⑨ → 출처 ⑩
>
> 바뀐 것은 셋이다.
> **(1)** 이용자 후기·평가를 요금 계산·주변 비교 **위로** 올렸다. 우리 차별화는 실제 사람이 남긴 평가인데, 입력 폼이 하단에 있으면 참여율이 오를 수 없다(실유저 리뷰 91건 / 87 lot = **0.27%**).
> **(2)** 후기 **목록을 입력 폼 앞에** 뒀다. 남의 평가를 먼저 읽어야 작성 동기가 생긴다.
> **(3)** ④ 를 ⑥ **바로 뒤로** 옮겼다. 둘 다 "여기 말고 어디"에 답하므로 붙어 있어야 한다. (④ 는 웹 후기 파생이지만 배치는 기능 기준을 따른다.)

| 표시 | ID | 블록 | 표시 조건 | 대상 lot | 비율 |
|---:|---|---|---|---:|---:|
| — | — | 헤더 + KPI 4종 | 항상 | 31,994 | 100% |
| 1 | ⓪ | 지도 · 로드뷰 · 길찾기 | 좌표 보유 | 31,994 | 100% |
| 3 | ⑧ | **이용자 후기 카드 목록** | 실유저 리뷰 1건 이상 | 87 | 0.27% |
| 4 | ⑦ | **평가 남기기 (작성 폼)** | 항상 | 31,994 | 100% |
| 5 | ① | 후기 종합 (한 줄 결론 + 자주 나온 말 + 라벨 목록) | `ai_summary` 2건 이상 | 배치 후 확정 | 미확인 |
| 2 | ② | **평가** — 이용자 별점 + 웹 후기 분위기 | 별점: 리뷰 1건↑ / 분위기: 유효 후기 3건↑ | 87 / 1,116 | 0.27% / 3.5% |

| 7 | ⑤ | 요금 계산 | `base_fee>0` **AND** `extra_*` 보유 | 5,420 | 16.9% |
| 8 | ⑥ | 주변 주차장 비교 (첫 행 = 현재 주차장 기준행) | 좌표 보유 | 31,994 | 100% |
| 9 | ④ | 함께 언급된 주차장 | 매칭 1건 이상 | 신규 | 미확인 |
| 10 | ⑨ | FAQ | 이미 구현됨 | — | — |
| 11 | ⑩ | 참고한 웹 후기 (링크만, **기본 접힘**) | 유효 소스 1건 이상 | 7,475 | 23.4% |

> **빈 페이지에서 상단이 비지 않는가** — ⑧ 은 실유저 리뷰 보유 **87 lot(0.27%)** 에서만 렌더한다.
> 리뷰가 없으면 ⑧ 을 그리지 않고 ⑦(입력 폼)만 남으므로 상단이 빈 카드로 시작하지 않는다.
> 나머지 **99.7%** 페이지에서는 ⑦ 이 사실상 첫 콘텐츠 블록이 되는데, 그것이 리뷰 선순환(전략 C)의 의도다.

### 근거 번호 규격

Google AI Overview 방식. 문장 끝에 `[n]` 번호를 달고, 누르면 ⑩ 출처 목록의 해당 항목이 강조된다.

- ⑩ 목록은 **기본 접힘** — "참고한 웹 글 n건 — 주차장 정보 모음 사이트 m건은 뺐습니다" 한 줄만 노출하고 펼쳐야 목록이 보인다
- 번호를 누르면 접혀 있어도 **자동으로 펼쳐지며** 해당 항목이 하이라이트된다
- 근거 번호 = ⑩ 목록의 순번 (분위기 점수 내림차순)
- 정보 모음 사이트·집계 제외 소스는 번호를 받지 않는다
- **원문 본문은 어디에도 렌더하지 않는다** — 제목 + 도메인 + 날짜 + 링크만

### ⚠️ 냉정한 현실

정제 레이어가 "꽉 찬" 페이지는 지금 **1,116곳 남짓(3.5%)**이다.
나머지 96%는 **요금 파생 + 주변 비교표 + FAQ + 구조화 데이터**로 채워지는 구조 데이터 페이지가 된다.

**그래서 구현 순서는 표시 순서와 다르다.** 표시는 사람 → 기계 → 돈 순이지만, **만드는 순서**는 커버리지가 넓은 것부터다:
전 lot에 적용되는 ⓪⑥⑦⑨ → 요금 계산 ⑤(5,420) → 정제 레이어 ①②③ → 신규 ④.

### ⑦ 블록의 선행 제약 (검증 단계에서 확정)

> **2026-09-02 결정** — 4축(진입·주차면·통로·출차)을 **입력으로 받지 않는다**. 항목별 점수를 요구하면 참여율이 더 떨어지고, "평가 남기기 → 별도 페이지"의 1depth에서 또 이탈한다.
> 입력은 현행 `ReviewForm` 그대로(종합 별점 0.5단위 하나 + 선택 코멘트, 상세페이지 인라인), 진입·주차면·통로·출차 구분은 **출력**으로 옮겨 ⑧ 블록에서 쌓인 리뷰 문장을 AI가 항목별로 요약한다. 항목 카드에는 별점이 아니라 요약 문구와 근거 리뷰 수만 노출한다.
> (뒤 문단의 항목별 요약·임계치 논의는 아래 2차 결정으로 대체됐다. 입력을 종합 별점 하나로 두는 부분은 그대로 유효하다.)
>
> **2026-09-02 2차 — 항목별 요약은 보류, 후기 원문 노출이 먼저다.** 시안 리뷰에서 "요약만 있고 정작 이용자 후기를 볼 수 없다"는 지적이 나왔다. ⑧을 항목별 요약이 아니라 **기존 카드 목록 형태의 이용자 후기 전체 노출**로 되돌린다.
> - 카드 규격은 현행 `UserReviewCard` 그대로 — 아바타 + 닉네임 + `StarDisplay` + 작성일 + 본문
> - 기존 아쉬움이던 **본문 잘림**은 5줄 클램프 유지 + 잘린 카드에만 **더보기**를 붙여 전문(1depth)으로 보낸다
> - 헤더에 `전체보기 n건` → `/wiki/{slug}/reviews`
> - 진입·주차면·통로·출차 항목별 AI 요약은 **폐기가 아니라 보류** — 리뷰가 쌓인 뒤 후기 목록 위 요약 스트립으로 다시 검토한다
>
> **별점 컴포넌트는 신규 제작하지 않는다.** 시안 초안이 별 1개 단위·자체 색상이었으나, 현행 `StarRatingInput`/`StarDisplay` 스펙(lucide `Star`, `yellow-400` 채움, 빈 별 회색 외곽선, 별 좌/우 절반 = 0.5점 히트존)을 그대로 쓴다.

| 사실 | 근거 | 함의 |
|---|---|---|
| **비회원 리뷰가 이미 허용된다** — IP/lot 24시간 1건 rate limit | `src/server/reviews.ts` | 로그인 장벽이 없어 ⑦' 작성 유도는 **즉시 배포 가능** |
| `parking_lot_stats`에 **4축 집계 컬럼이 없다** | remote DDL 확인 | 4축 별점 표시를 접었으므로 **마이그레이션 불필요** — 종합 별점만 집계한다 |
| `user_reviews`의 4축은 `REAL NOT NULL CHECK(0.5~5)`, **`overall_score`도 NOT NULL** | remote DDL | 현행 `ReviewForm`이 종합 별점을 4축에 그대로 복사해 넣어 이미 충족 — 입력 UI 변경 없음 |
| `parking_lot_stats.review_count > 0` = 147 lot / SUM 232 — **시드 143건 포함** | remote 실측 | 별점 게이트는 `is_seed=0` 기준으로 걸어야 한다 (87 lot) |

### 차별화 지점은 "안 그리는 것"이다

경쟁사는 데이터가 없어도 템플릿을 채워 발행한다. 우리는 반대로 간다 —
**후기 3건 미만이면 ①②를 렌더하지 않고, 요금이 없으면 ⑤를 숨긴다.**
비어 있는 페이지가 값이 0인 페이지보다 낫다.

## 7. 검증 지표

> **⚠️ 초안 KPI 폐기 (2026-09-02)** — 초안은 "가시 텍스트 2,000자 이상, 자체 비중 100%"를 1단계 목표로 삼았다. **둘 다 잘못된 지표다.**
>
> - **글자 수는 품질 지표가 아니다.** 경쟁사가 2,381자로 우리보다 많지만 그 안에 `0min 0`, "1시간 예상 요금은 0원입니다" 같은 페이지가 섞여 있다. 분량을 목표로 잡으면 그쪽으로 간다.
> - **"자체 콘텐츠 100%"는 우리 편의상의 정의다.** B1~B7은 이미 있는 DB 값을 계산·조합한 것이고, 그것을 검색엔진이 독창적 편집 콘텐츠로 인정한다고 볼 근거는 없다. 유용한 기능인 것과 고유 가치로 인정받는 것은 별개다.
>
> 아래는 **정확성·유효성·사용자 행동**으로 교체한 지표다.

| 단계 | 무엇을 보고 성공을 판단하는가 | 지금 잴 수 있나 |
|---|---|---|
| 0단계 | 정보 모음 사이트 소스 수 → **0** | ✅ SQL |
| 0단계 | 크롬 토큰(`skip to main`, `CATEGORY` 등) 포함 `ai_summary` 수 → **0** | ✅ SQL |
| 0단계 | **잘못된 요금·주소·lot 매칭 건수 → 0** (샘플 감사) | ✅ 수동 표본 |
| 1단계 | **주차장별 유효 데이터 커버리지** — 요금 계산 가능 5,420 / 운영시간 25,216 / 면수 15,986을 각각 얼마나 끌어올렸나 | ✅ SQL |
| 1단계 | 요금 계산기가 **"계산 불가"를 정직하게 표시하는 비율** — 결손 3,846건에 숫자를 지어내지 않는지 | ✅ SQL + 라이브 |
| 2단계 | **원문 복사 문장 → 0** (SSR HTML에서 스크랩 본문 글자수) | ✅ 라이브 크롤 |
| 2단계 | **AI 요약 정확도·유효 매칭률** — 커버리지 80%가 아니라 *맞는 요약* 비율 | ⚠️ 표본 QA 필요 |
| 3단계 | ④ 대안 주차장 매칭의 **정밀도**(오매칭 0 우선) | ⚠️ 표본 QA 필요 |
| 3단계 | 상세페이지당 내부 링크 수 | ✅ 라이브 |
| 전 구간 | **리뷰 작성 전환율** (페이지뷰 → 제출) | ❌ 애널리틱스 도입 선행 |
| 전 구간 | **페이지별 사용자 행동 완료율** (길찾기·전화 클릭 등) | ❌ 애널리틱스 도입 선행 |
| 전 구간 | GSC 색인율 / 노출 / 클릭 변화 | ❌ 사장님이 GSC에서 직접 확인 |

> **표시된 ❌ 세 항목은 지금 측정 수단이 없다.** 애널리틱스가 없으면 전환율·행동 완료율은 잴 수 없고, GSC는 우리가 접근할 수 없다. "측정하겠다"고 적어두고 안 재는 것보다, **선행 조건을 명시**하는 편이 정직하다.
>
> GSC 지표는 **관찰만 한다.** v2 적용과 색인 증가 사이의 인과는 우리가 통제 실험을 할 수 없으므로 단정하지 않는다.
