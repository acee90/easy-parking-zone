### 2-2. 두 갈래 가설 — 규모가 약 10배 다르다

> **수치 정정 (2026-09-02)**: 초안은 B의 규모를 "web_sources 3건 이상 2,246 lot"으로 적었으나 이 값은 어느 출처에도 대응하지 않았다. remote 재측정 결과 **rel≥40 소스 3건 이상 = 1,678 lot**, 관련성 무관 전체 기준은 2,305 lot이다. 상세페이지는 rel≥40만 렌더하므로 **1,678이 정직한 기준**이다.

- **가설 A (thin)**: 페이지에 고유 콘텐츠가 없어서 색인 가치가 없다 → 해당 규모 **sitemap 18,017의 약 90.7%**
- **가설 B (스크랩 오염)**: 콘텐츠가 있는 페이지가 남의 글/중복/무관 텍스트라 신뢰를 못 얻는다 → 해당 규모 **rel≥40 web_sources 3건 이상 1,678 lot = sitemap의 약 9.3%** (전체 web_sources 기준으로 넓게 잡아도 2,305 lot = 12.8%)

**두 문제는 별개 트랙이고, 규모 기준으로는 A가 약 10배 크다.** 다만 B는 "트래픽이 실제로 붙을 페이지"에 집중돼 있어(priority sitemap 표본에서 scrap:own 중앙값 2.41 [라이브]) 우선순위를 규모만으로 정하면 안 된다.

### 2-3. GSC에서 어떤 리포트를 봐야 A/B가 갈리는가

`Search Console > 색인 생성 > 페이지` 리포트의 "색인이 생성되지 않은 이유"에서 다음 두 항목을 비교하라.

| GSC 상태 | 의미 | 무엇을 가리키는가 | 이 문서의 대응 |
|---|---|---|---|
| **크롤링됨 - 현재 색인이 생성되지 않음** (Crawled – currently not indexed) | Googlebot이 **페이지를 실제로 가져가서 내용을 봤고**, 본 뒤에 색인할 가치가 없다고 판단 | **콘텐츠 품질 문제.** thin / 중복 / 남의 글 / 템플릿 양산 판정 | 전략 A(스크랩 정리) + 전략 B(자체 레이어)가 정답 |
| **검색됨 - 현재 색인이 생성되지 않음** (Discovered – currently not indexed) | URL 존재는 알지만 **크롤을 아직 하지 않았다** | **주요 가설**: 크롤 예산 / 사이트 중요도 / 내부링크. 페이지 내용은 아직 평가 대상이 아닐 가능성이 높다 | sitemap 축소·내부링크 강화·[7월감사] RC-4(지역 허브 없는 lot 52.9%)를 **먼저** 시도한다. 다만 "콘텐츠 개선으로는 안 풀린다"고 단정하지 말 것 — 사이트 전반의 품질 신호가 크롤 우선순위에 영향을 준다는 해석도 가능하고, **우리는 그 인과를 측정한 바 없다** |

**판별 절차 (사람이 GSC에서 30분 안에)**
1. 두 상태의 **절대 건수와 비율**을 기록. 어느 쪽이 큰지가 트랙을 결정한다.

#### ⚠️ B3 정정 (2026-09-02) — 초안 공식은 유료 lot의 33%에서 틀린 값을 낸다

초안은 `transforms.ts:117-123`의 SQL 필터 근사식 `base_fee * 60.0 / base_time`을 그대로 화면에 쓰자고 했다. **그 식은 추가 단위요금(`extra_time`/`extra_fee`), 올림 처리, 일 최대요금을 전혀 반영하지 못한다.** 필터용 근사로는 허용되지만 사용자에게 보여줄 금액이 아니다.

**정식 공식**

```
이용시간 ≤ base_time              → base_fee
이용시간 > base_time              → base_fee + ceil((이용시간 - base_time) / extra_time) × extra_fee
daily_max 가 있으면               → min(위 결과, daily_max)
extra_time / extra_fee 가 없으면  → 계산하지 않고 "요금 정보 부족"으로 표시
```

**오차 실례** (근사식 → 정식)

| 요금제 | 근사식 | 정식 | 오차 |
|---|---:|---:|---|
| 기본 30분 3,000원 + 15분당 1,000원 | 6,000원 | 5,000원 | **+20% 과대** |
| 기본 20분 2,000원 + 10분당 1,200원 | 6,000원 | 6,800원 | **−12% 과소** |
| 기본 30분 1,000원 + 15분당 500원 | 2,000원 | 2,000원 | 일치 |

양방향으로 틀린다. 두 식이 일치하는 건 `extra_time == base_time && extra_fee == base_fee`일 때뿐이다.

**모수 재측정 (remote D1, 2026-09-02)**

| 구분 | 건수 | 비율 |
|---|---:|---:|
| `base_fee>0 AND base_time>0` | 9,266 | 100% |
| └ `extra_time≠base_time` 또는 `extra_fee≠base_fee` → **근사식 오답** | **3,057** | **33.0%** |

> **결손 3,846건에 근사식을 적용하면 숫자를 지어내게 된다.** 경쟁사가 `/parking/9000`에서 "1시간 예상 요금은 0원입니다"를 내보낸 것과 같은 종류의 실패다(§5 "따라하지 않는다"). B3/B5의 커버 lot은 9,448이 아니라 **5,420**으로 정정한다.

| 근거 | 내용 |
|---|---|
| 참여율 | 항목이 4개면 이탈이 는다. 실유저 리뷰가 **91건(87 lot, 0.27%)** 인 콜드스타트 단계에서 입력 마찰을 늘릴 여유가 없다 |
| 현행 코드 | `ReviewForm.tsx:39`는 이미 **종합점수 하나를 4축에 그대로 복사**한다. 즉 지금 DB의 4축 값은 전부 동일값이라 축별 정보량이 0이다 |
| 스키마 | 4축·`overall_score` 모두 `REAL NOT NULL CHECK(0.5~5)`. 현행 복사 방식으로 제약을 이미 충족하므로 **마이그레이션도 입력 UI 변경도 불필요** |

**따라서 B9(4축 난이도)도 "축별 별점·축별 평균 표시"를 이번 범위에서 뺀다.** 축별 정보가 실제로 쌓이기 전까지는 표시할 것이 없다. 대신 코멘트에 명시적으로 언급된 경우에만 "진입로 관련 언급 N건" 같은 형태로 노출하고, 이는 리뷰가 충분히 쌓인 뒤 재검토한다.

> **제출 경로는 이미 열려 있다 (2026-09-02 코드 확인)** — `src/server/reviews.ts`는 **비회원 리뷰를 허용**하고(`guest_nickname` 기본 '익명', `ip_hash` 저장) rate limit은 **비회원 IP+주차장 24시간 1건 / 회원 주차장당 24시간 1건**이다. 즉 C1·C2는 로그인 장벽 없이 배포 가능하며, 이는 선순환의 가장 큰 마찰이 이미 제거돼 있다는 뜻이다. 초안은 이 사실을 언급하지 않았다.

> **이 절에서 아직 얕은 부분 (요구사항 "리뷰 기반 차별화" 대비 미완)** — 다음 세 가지는 본 문서가 다루지 않았고, 후속 문서가 필요하다.
> 1. **개별 `Review` 구조화 데이터**: §6-1 diff는 `AggregateRating`만 다루고 개별 리뷰 마크업(`Review` + `author` + `reviewRating`)은 목록에 없다. 실유저 리뷰가 쌓이면 AggregateRating과 함께 넣어야 SERP 효과가 나는데, 여기서도 **is_seed=0만** 대상이어야 한다.
> 2. **스팸·품질 관리**: 비회원 제출이 열려 있고 24시간 1건 제한뿐이므로, 리뷰가 늘면 신고/차단/삭제 경로와 코멘트 검수 기준이 필요하다. 검수 없는 UGC를 페이지 본문으로 쓰는 것은 §8에서 경쟁사를 비판한 근거(콘텐츠 신뢰)와 같은 리스크를 우리 쪽에 만든다.
> 3. **콜드스타트 산술**: "87 → 3개월 500 lot"의 근거가 없다. 필요한 것은 (상세페이지 주간 세션 수) × (위젯 노출률) × (제출 전환율)인데 **현재 트래픽 실측치가 문서에 없어 계산 자체가 불가**하다. C1 배포 후 1주 실측으로 기준선을 잡기 전까지 이 목표는 **미확인 가정**이다.

### 5-4. 선순환 논리

```
리뷰 1건 → 4축 점수 노출(자체 콘텐츠 +) → 페이지가 thin 그룹 이탈
        → AggregateRating 정당하게 출력 가능 → SERP 별점 → CTR
        → 트래픽 → 리뷰 진입점 노출 증가 → 리뷰 N건
```

**경쟁사는 현재 이 고리를 갖고 있지 않다** (구조적으로 불가능하다는 뜻은 아니다 — 리뷰 수집 기능을 붙이면 따라올 수 있다). 관측 시점 기준 경쟁사 JSON-LD에 AggregateRating이 없고, /post 2,474건(2026-09-02 재측정)은 자동 생성물이면서 "저는 직접 주변을 둘러보고", "제가 실제로 걸어본 동선을" 같은 **1인칭 체험을 허위 서술**한다(po3에서 6회 검출). 실제 사용자 평가는 우리만 가질 수 있는 축이다.

**현실적 목표 설정**: 87 → 3개월 500 lot 수준을 노리되(**이 숫자는 근거 없는 목표치다 — 트래픽 실측 전까지 미확인**, §5-3 주석 3 참조), **리뷰로 31,994 페이지를 채울 수는 없다.** 리뷰는 상위 수천 페이지의 차별화 무기이고, 나머지는 전략 B의 파생 콘텐츠가 맡는다.

### 6-2. ⚠️ AggregateRating — 현재 코드는 정책을 지키지 않는다

**코드 (`src/lib/parking-jsonld.ts:33-41`, 발췌 — `'@type'`/`bestRating`/`worstRating` 줄 생략)**

```
...(lot.difficulty.score !== null && {
  aggregateRating: {
    '@type': 'AggregateRating',
    ratingValue: lot.difficulty.score.toFixed(1),
    bestRating: '5',
    worstRating: '1',
    ratingCount: lot.difficulty.reviewCount || 1,
  },
}),
```

> 척도 자체는 정상이다 — remote `final_score` 범위는 1.52~4.38로 `worstRating: '1'` ~ `bestRating: '5'` 안에 든다. 아래 세 문제는 척도 오류가 아니라 **출력 대상과 의미**의 문제다.

**세 가지 문제**

| # | 문제 | 근거 |
|---|---|---|
| 1 | **출력 게이트가 리뷰가 아니라 난이도 점수다.** `parking_lot_stats` 31,939행(99.8%)이 `final_score`를 갖고 있으므로 사실상 전 페이지가 리뷰 마크업을 출력한다. 반면 실유저 리뷰가 있는 lot은 **87개(0.27%)** | remote + 코드 |
| 2 | **`ratingCount: reviewCount \|\| 1` 은 리뷰 0건일 때 1을 지어낸다.** 존재하지 않는 평가 1건을 구조화 데이터로 선언하는 것. 게다가 이 `reviewCount`는 `parking_lot_stats.review_count`(`parking.ts` `COALESCE(s.review_count,0)`)이고 remote 실측 `review_count>0` = **147 lot / SUM 232** 로 **시드 리뷰 143건을 포함한다** → 0건일 때 1을 지어내는 것과 별개로, 0이 아닌 경우에도 시드가 섞여 있다(C7이 선행돼야 하는 이유) | 코드 `:39` + remote |
| 3 | **의미 왜곡** — `ratingValue`에 들어가는 값은 사용자 만족도가 아니라 **주차 난이도 점수**이고, 그중 실제 근거가 있는 것은 `n_effective>0` = 1,239 lot(3.9%)뿐. 나머지 96.0%는 structural/none(주차장 유형·면수에서 유도한 사전확률) | remote |

**권고 (우선순위 최상 — 색인 이득이 아니라 리스크 제거)**

```
출력 조건을 다음으로 교체:
  실유저 리뷰(is_seed=0) count >= 1  AND  ratingValue = 리뷰 기반 값  AND  ratingCount = 실제 건수
그 외에는 aggregateRating 키를 아예 내보내지 않는다.
```

- 적용 시 마크업 출력 lot: ~31,939 → **87**. 급감이지만 **정당한 87건**이다.
- 난이도 점수는 별점이 아니라 `additionalProperty`(PropertyValue)로 내보내면 의미 왜곡 없이 유지할 수 있다.
- 이 수정은 전략 C(리뷰 선순환)의 전제다. 리뷰가 쌓이는 만큼 정당하게 출력 대상이 늘어난다.

#### 색인 판정 일원화 대상 — 네 곳이 서로 다르다 (2026-09-02 확대)

초안은 `sitemap-handler.ts` 두 줄과 robots 게이트만 다뤘으나, 실제로는 **네 개의 서로 다른 판정**이 공존한다.

| # | 판정 지점 | 현재 조건 |
|---|---|---|
| 1 | `sitemap-index` / `sitemap-N` | `sitemap-handler.ts:305` — web_sources 존재 OR ai_summary OR curation_reason OR 기본필드 3개↑ (`is_free IS NOT NULL` 죽은 신호 포함) |
| 2 | `sitemap-parking` | 별도 쿼리 |
| 3 | `sitemap-priority` | `getPriorityParkingRows(db, limit)` — **상위 N개 고정 슬롯**(현재 200), 조건이 아니라 정렬+절단 |
| 4 | 상세페이지 robots 메타 | `shouldIndexParkingDetail()` (`src/lib/seo-indexing.ts`) — rel≥40 콘텐츠 1건↑ OR editorial 10자↑ OR SEO 신호 3개↑ |

1과 4의 불일치만으로도 **등재됐는데 noindex ≈264 lot / 게이트는 통과하는데 미등재 ≈7,348 lot**이 생긴다(SQL 근사치, §1-5). 3은 조건이 아니라 슬롯이라 성격 자체가 다르다.

**처방**: `isIndexableParkingDetail(lot): boolean` 하나를 만들어 1·2·4가 전부 그것만 호출하게 한다. 3은 "색인 여부"가 아니라 "우선순위"이므로 판정 함수 통과분 안에서 정렬하는 구조로 바꾼다.

**검증 지표**: rel≥40 ai_summary 보유율 80% 도달 · 폴백 제거 후 블로그 섹션이 비는 lot 4,441 → 1,800 이하 · lot AI 요약 22 → 1,000 이상(QA PASS+FIX 80%↑, DROP 20%↓ 게이트 준수) · sitemap 등재 URL 중 thin 비율 → 20% 이하 · GSC 색인 생성됨 페이지 수 절대값.

> **thin 지표의 정의를 하나로 고정할 것.** 본 문서에는 두 정의가 섞여 있었다 — §1-4/F2의 **7,500 (41.6%)** 은 `web_sources 없음 AND stats.ai_summary NULL AND curation_reason NULL`, 리뷰·영상·curation_tag까지 추가로 제외한 엄격 정의는 **7,492** 다(둘 다 remote 2026-09-02). 추적 지표는 **7,500 기준(41.6% → 20%)** 으로 통일한다.

> **AI 콘텐츠 게이트는 이미 확정돼 있다**: `ai-content-rollout-plan.md:16-21`(Pilot 50 → Batch 300 → 1,000 → 10k+), `:25-31`(PASS+FIX 80%↑ / 공식데이터 충돌률 5%↓ / DROP 20%↓ / 유사 템플릿 10건 미만). 현재 lot AI 요약 22건은 **Pilot 단계도 미완**이다.
