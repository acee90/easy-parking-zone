## 2. 새로 드러난 것 — 사이트맵이 Google에게 거짓말을 하고 있다

`sitemap-handler.ts:76-88`(과 `:341-353`, 동일 블록 2벌)의 포함 조건:

```sql
WHERE EXISTS (web_sources ... AND filter_passed_v2 IS NOT 0)
   OR s.ai_summary IS NOT NULL
   OR p.curation_reason IS NOT NULL
   OR ( total_spaces>0 + phone非빈 + is_free IS NOT NULL + curation_tag非NULL ) >= 3
```

**4번째 가지가 문을 열어놨다.** `is_free`는 `integer(...).notNull().default(false)`(`schema.ts:94`)라 `IS NOT NULL`이 **항상 1**이다. 따라서 저 조건은 실질적으로 **나머지 3개 중 2개**만 있으면 통과다 — 면수와 전화번호만 있으면 들어온다. 콘텐츠 신호가 아니다.

파일 헤더 주석(`:8`, `:16`)은 *"sitemap-N.xml : web_sources 있는 주차장 / thin 주차장은 완전 제외(#126)"* 라고 적혀 있지만 **코드는 그렇게 동작하지 않는다.**

### 측정 결과 — remote D1 전수 (2026-09-09)

`bunx wrangler d1 execute parking-db --remote --command "…"` 로 전수 확인했다.
**검증: `now_included` = 20,286 으로 라이브 sitemap 실측값과 정확히 일치** → 술어 해석이 맞다.

|---|---:|---|
| ① 웹 출처(`filter_passed_v2 IS NOT 0`) | **6,194** | |
| ② lot AI 요약 | **682** | 대부분 ①의 부분집합 |
| ③ 큐레이션 사유 | **112** | |
| ④신 실유저 리뷰(`is_seed=0`) | **93** | |

**M1 적용 시 20,286 → 6,397 (−68.5%, 13,889건 제거).**

> **구조적 사실 하나**: ①만으로 6,194이고 합집합이 6,397이다. ②③④신이 더하는 건 **203건**뿐이다.
> AI 요약·큐레이션은 웹 출처에서 파생되므로 거의 전부 ①의 부분집합이다.
> 즉 **새 게이트는 실질적으로 "웹 출처 보유 lot"** 이다.

> **표본 추정 대비 정확도** — 표본(115건)으로 추정했던 값과 전수의 차이:
> 웹출처 ~6,500 → **6,194** (적중), AI요약 ~600 → **682** (적중),
> 큐레이션 ~800 → **112** (7배 과대), 리뷰 ~600 → **93** (6배 과대).
> 뒤 둘은 표본에서 4/115, 3/115로 잡힌 희귀 사건이라 외삽 오차가 컸다.
> 합집합 추정 ~6,900 → 실제 **6,397** 은 95% CI(5,100~8,700) 안에 들었다.

sitemap 밖(noindex) 표본은 100% thin — 차단 자체는 동작한다. 문제는 **차단선이 너무 아래에 그어져 있다**는 것이다.

### 왜 이게 최우선인가

Google에게 "색인할 가치가 있다"고 신고한 20,286개 중 **약 13,400개가 공공데이터 필드 치환 + 자동 FAQ + 주변 주차장 표뿐이다.** 이건 경쟁사 mustarddata가 32,184개로 하고 있는 것과 **정확히 같은 종류의 페이지**다. 그 축에서는 이길 수 없다 — 저쪽은 정적 파일이라 TTFB가 10배 빠르고 페이지 수도 1.5배다.

우리가 이길 수 있는 축(난이도·리뷰·AI 요약)은 **색인 대상의 7%**(AI요약 3% + 리뷰 3% + 큐레이션 4%의 합집합, 중복 제외 시 ~7%)뿐이다.

**보강의 방향은 "넓히기"가 아니라 "모으기"다.**

## 3. Gate 0 — 답이 나왔다 (2026-09-09 GSC 실측)

| 사유 | 건수 | 비율 |
|---|---:|---:|
| **발견됨 – 현재 색인이 생성되지 않음** | **16,811** | **99.86%** |
| 크롤링됨 – 현재 색인이 생성되지 않음 | 22 | 0.13% |
| 리디렉션 오류 | 1 | 0.01% |

**이건 콘텐츠 품질 문제가 아니다.** Google이 URL 존재는 알지만 **아직 가져가지도 않았다.**
실제로 크롤한 뒤 색인을 거절한 건 **22건**뿐이다 — 즉 **Google이 우리 페이지를 열어보면
대체로 색인한다.** 병목은 "무엇을 보여주느냐"가 아니라 **"얼마나 가져가느냐"** 다.

주목할 점 하나: `noindex 태그에 의해 제외됨` 항목이 **아예 없다.** noindex는 크롤해야
알 수 있으므로, ~33,786개 noindex 페이지도 대부분 아직 크롤되지 않았다는 뜻이다.

### 이 수치가 뒤집는 것

9/2 문서 §2-3이 예고한 대로다 — *"`검색됨-미색인`이 지배적이면 sitemap 축소·내부링크
강화를 **먼저** 시도한다"*.

- **M2(AI 요약 확대)는 지금 돈을 쓸 곳이 아니다.** Google이 안 가져가는 페이지의 내용을
  좋게 만들어도 평가 대상이 되지 않는다. (단 9/2 문서의 유보 그대로 — 사이트 전반의
  품질 신호가 크롤 우선순위에 영향을 준다는 해석도 가능하고, 우리는 그 인과를 측정한 바 없다.)
- **크롤 예산을 늘리거나, 예산이 쓰이는 대상을 줄이거나** 둘 중 하나다. 전자는 도메인 권위
  (외부 링크)와 응답 속도의 함수라 단기 조작이 어렵다. **후자는 오늘 할 수 있다.**

### 3-1. 크롤링 통계 — 진짜 병목이 여기 있다 (2026-09-09 GSC)

| 항목 | 값 |
|---|---|
| 총 크롤링 요청 (26.6.11~26.9.7, 88일) | **962** |
| **하루 평균** | **10.9건** |
| 총 다운로드 | 48.1 MB (요청당 ~50KB) |
| **평균 응답 시간** | **220 ms** |
| 호스트 상태 | easy-parking.xyz 958 · www 4 — **둘 다 "문제 없음"** |

**Google은 이 사이트를 크롤하는 데 하루 2.4초를 쓴다** (10.9건 × 220ms).

| 크롤 대상 | 1회전 소요 |
|---|---:|
| 현재 54,600 | **13.7년** |
| M1-a + `/wiki/all` 정리 후 6,500 | **1.6년** |
| AI요약·리뷰 보유분 1,350만 | 4개월 |

### 이 수치가 뒤집는 것 — M3(TTFB)는 크롤 레버가 아니다

**응답 속도는 병목이 아니다.** Google이 재는 평균 응답이 **220ms**이고 상태는 "문제 없음"이다.
(내 curl 실측 0.9~1.8초와 다른 이유는 Google이 Cloudflare 엣지에 붙기 때문으로 보인다.)
하루 2.4초를 쓰는 크롤러가 서버 용량 때문에 막혔을 리 없다.

즉 이건 **크롤 용량(capacity) 한계가 아니라 크롤 수요(demand) 한계**다.
Google이 *못* 가져가는 게 아니라 **가져갈 만하다고 보지 않는다.**

크롤 수요를 결정하는 건 **도메인 권위**다. `.xyz` 신규 도메인 + 외부 백링크 0(#161 진단 1번).
네이버는 같은 사이트를 1.2만 색인했다 — 콘텐츠·기술 문제가 아니라는 방증이다.

> **정리(M1-a, `/wiki/all`)는 여전히 할 가치가 있지만 해결책은 아니다.**
> 하루 10.9건 중 색인 후보에 닿는 게 **1.3건 → 10.8건**으로 8배가 된다. 싸고 확실한 이득이다.
> 그러나 1회전이 13.7년에서 1.6년이 될 뿐, 여전히 사업적으로 의미 있는 속도가 아니다.

### 추가로 필요한 숫자

**GA4의 `/wiki` 주간 세션 수** — 9/2 문서 §5-3 주석 3이 지적한 대로, 이 값 없이는
리뷰 목표치를 세울 수 없다.

> **M1은 사람 결정이다.** 전수 확인 결과 **20,286 → 6,397 (−68.5%, 13,889건 제거)**.

> 그것들이 나머지 1/3의 크롤 순번을 밀어내고 있다. 9/2 문서도
> *"31,994 다 넣기는 목표가 아니다"* 라고 적었다.

#### M1 은 2단계로 나눈다 (되돌릴 수 있게)

한 번에 sitemap 제거 + `noindex` 를 동시에 걸면, 이미 색인된 페이지가 그 13,889건 안에
있을 경우 색인에서 빠진다. 되돌리기 어렵다.

| 단계 | 내용 | 되돌리기 | 효과 |
|---|---|---|---|
| **M1-a** | **sitemap 술어만 교체.** robots 는 건드리지 않는다(`index` 유지). 대상 URL 은 `/wiki/all` 로 여전히 도달 가능 | 쉬움 — 술어만 되돌리면 복귀 | 크롤 큐 20,286 → 6,397. **색인 손실 0** |
| **M1-b** | `shouldIndexParkingDetail` 을 같은 술어로 통일해 `noindex` 부여 | 어려움 (churn) | 크롤 자체를 막는다 |

**M1-a 를 먼저 배포하고 GSC 크롤링 통계·색인 건수를 2~4주 관찰한 뒤 M1-b 를 판단한다.**

M1-b 판단에 필요한 값: **GSC `색인 생성됨` 건수**와, 그중 13,889건에 속한 URL 비율.
색인된 게 거의 없다면 M1-b 는 손실 없이 진행 가능하다.

> RC-2(`is_free IS NOT NULL` 죽은 신호) 수정은 M1-a 에 포함된다 — 4번째 가지를 통째로
> 제거하므로 죽은 신호도 같이 사라진다. **호출부 2곳(`:85`, `:350`)을 함께 고쳐야**
> sitemap index 의 pageCount 와 실제 URL 수가 어긋나지 않는다.
