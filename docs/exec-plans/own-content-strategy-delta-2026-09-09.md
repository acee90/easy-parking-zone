## 2. 새로 드러난 것 — 사이트맵이 Google에게 거짓말을 하고 있다

`sitemap-handler.ts:76-88`(과 `:341-353`, 동일 블록 2벌)의 포함 조건:

```sql
WHERE EXISTS (web_sources ... AND filter_passed_v2 IS NOT 0)
   OR s.ai_summary IS NOT NULL
   OR p.curation_reason IS NOT NULL
   OR ( total_spaces>0 + phone非빈 + is_free IS NOT NULL + curation_tag非NULL ) >= 3
```

**4번째 가지가 문을 열어놨다.** `is_free`는 `integer(...).notNull().default(false)`(`schema.ts:94`)라 `IS NOT NULL`이 **항상 1**이다. 따라서 저 조건은 실질적으로 **나머지 3개 중 2개**만 있으면 통과다 — 면수와 전화번호만 있으면 들어온다. 콘텐츠 신호가 아니다.

파일 헤더 주석(`:8`, `:16`)은 *"sitemap-N.xml : web_sources 있는 주차장 / thin 주차장은 완전 제외(#126)"* 라고 적혀 있지만 **코드는 그렇게 동작하지 않는다.**

### 측정된 결과 (sitemap 색인대상 115건 표본)

| 구분 | 비율 | 20,286 대비 추정 |
|---|---:|---:|
| 웹 출처 보유 | 32% (±9%p) | ~6,500 |
| 큐레이션 사유 보유 | 4% (±4%p) | ~800 |
| lot AI 요약 보유 | 3% (±3%p) | ~600 |
| 리뷰 보유 | 3% (±3%p) | ~600 |
| **넷 다 없음 = 순수 템플릿 껍데기** | **66% (±9%p)** | **~13,400** |

sitemap 밖(noindex) 표본 5건은 100% 순수 thin — 차단은 정상 동작한다. 문제는 **차단선이 너무 아래에 그어져 있다**는 것이다.

### 왜 이게 최우선인가

Google에게 "색인할 가치가 있다"고 신고한 20,286개 중 **약 13,400개가 공공데이터 필드 치환 + 자동 FAQ + 주변 주차장 표뿐이다.** 이건 경쟁사 mustarddata가 32,184개로 하고 있는 것과 **정확히 같은 종류의 페이지**다. 그 축에서는 이길 수 없다 — 저쪽은 정적 파일이라 TTFB가 10배 빠르고 페이지 수도 1.5배다.

우리가 이길 수 있는 축(난이도·리뷰·AI 요약)은 **색인 대상의 7%**(AI요약 3% + 리뷰 3% + 큐레이션 4%의 합집합, 중복 제외 시 ~7%)뿐이다.

**보강의 방향은 "넓히기"가 아니라 "모으기"다.**

## 3. Gate 0 — 답이 나왔다 (2026-09-09 GSC 실측)

| 사유 | 건수 | 비율 |
|---|---:|---:|
| **발견됨 – 현재 색인이 생성되지 않음** | **16,811** | **99.86%** |
| 크롤링됨 – 현재 색인이 생성되지 않음 | 22 | 0.13% |
| 리디렉션 오류 | 1 | 0.01% |

**이건 콘텐츠 품질 문제가 아니다.** Google이 URL 존재는 알지만 **아직 가져가지도 않았다.**
실제로 크롤한 뒤 색인을 거절한 건 **22건**뿐이다 — 즉 **Google이 우리 페이지를 열어보면
대체로 색인한다.** 병목은 "무엇을 보여주느냐"가 아니라 **"얼마나 가져가느냐"** 다.

주목할 점 하나: `noindex 태그에 의해 제외됨` 항목이 **아예 없다.** noindex는 크롤해야
알 수 있으므로, ~33,786개 noindex 페이지도 대부분 아직 크롤되지 않았다는 뜻이다.

### 이 수치가 뒤집는 것

9/2 문서 §2-3이 예고한 대로다 — *"`검색됨-미색인`이 지배적이면 sitemap 축소·내부링크
강화를 **먼저** 시도한다"*.

- **M2(AI 요약 확대)는 지금 돈을 쓸 곳이 아니다.** Google이 안 가져가는 페이지의 내용을
  좋게 만들어도 평가 대상이 되지 않는다. (단 9/2 문서의 유보 그대로 — 사이트 전반의
  품질 신호가 크롤 우선순위에 영향을 준다는 해석도 가능하고, 우리는 그 인과를 측정한 바 없다.)
- **크롤 예산을 늘리거나, 예산이 쓰이는 대상을 줄이거나** 둘 중 하나다. 전자는 도메인 권위
  (외부 링크)와 응답 속도의 함수라 단기 조작이 어렵다. **후자는 오늘 할 수 있다.**

### 추가로 필요한 숫자 2개

1. **GSC > 설정 > 크롤링 통계**의 일일 크롤 요청 수 — 20,286개를 소진하는 데 걸릴 시간을
   계산할 수 있다. 하루 200건이면 100일, 2,000건이면 10일이다. M1의 효과 크기가 여기서 나온다.
2. **GA4의 `/wiki` 주간 세션 수** — 9/2 문서 §5-3 주석 3이 지적한 대로, 이 값 없이는
   리뷰 목표치를 세울 수 없다.

## 4. 우선순위

GSC가 `발견됨-미색인` 99.86%로 나왔으므로 **크롤 예산 트랙이 1순위**다.

### 1순위 — 크롤 예산 (지금)

| # | 조치 | 근거 | 비용 |
|---|---|---|---|
| **M1** | **색인 게이트 일원화·강화** — sitemap 4번째 가지 제거, `shouldIndexParkingDetail`과 같은 술어로 통일. 새 기준: 웹출처 ≥1 **or** 리뷰 ≥1 **or** AI요약 **or** 큐레이션 사유. RC-2 죽은 신호를 2곳(`:85`, `:350`) 동시 수정 | §2·§3 — 크롤 큐 20,286 → **~6,900**. 같은 크롤 속도로 소진 시간이 1/3 | S~M |
| **M3** | **TTFB 단축** — wiki 상세·허브에 Cache API/KV | 현재 0.9~1.8초. 크롤 속도는 응답 시간에 반비례한다. 경쟁사는 정적 파일(~0.1초) | M |
| **M7** | **홈을 크롤 진입점으로 되살리기** | `/`는 도메인에서 가장 자주 크롤되는 페이지인데 raw HTML 38단어·콘텐츠 링크 1개다. 크롤 확산의 출발점 | S~M |

M1과 M3는 **곱셈 관계**다. 대상을 1/3로 줄이고 속도를 2배로 올리면 소진 시간은 1/6이 된다.

> **M1은 여전히 사람 결정이다.** 색인 대상을 의도적으로 66% 걷어내는 일이고, 나중에
> 되돌리면 Google에 churn으로 보인다. 다만 GSC 수치가 이 결정을 강하게 지지한다 —
> 크롤되지 않은 16,811개 중 약 2/3가 템플릿 껍데기인데, 그것들이 나머지 1/3의
> 크롤 순번을 밀어내고 있다. 9/2 문서도 *"31,994 다 넣기는 목표가 아니다"* 라고 적었다.
>
> **실행 전 remote D1 전수로 새 술어의 통과 건수를 확인할 것**(§5).

### 하지 말 것

- **M2를 지금 먼저 하는 것.** Google이 안 가져가는 페이지의 내용을 개선해도 평가 대상이 되지 않는다. 크롤된 22건 중 색인 거절이 22건이라는 사실은 "내용이 나쁘다"가 아니라 "표본이 22건뿐"이라는 뜻이다.
- **넓히기**: 남은 33,786개 thin lot을 색인 대상으로 올리는 것. 크롤 예산이 이미 병목인데 큐를 3배로 늘리는 셈이다.
- **트래픽 실측 없이 리뷰 목표 세우기**: 9/2 문서가 이미 거부한 것.

## 5. 표본 한계

전부 115건(sitemap) / 5건(noindex) 표본 기반이며 ±는 95% 신뢰구간이다. remote D1 전수 조회가 아니다 — `.dev.vars`에 `D1_PROXY_TOKEN`이 없어 이 세션에서는 D1 직접 조회가 불가능했다. **M1을 실행하기 전에 새 술어의 통과 건수를 remote에서 전수로 확인할 것.** 추정 ~6,900이 실제로 몇 건인지에 따라 판단이 달라질 수 있다.
